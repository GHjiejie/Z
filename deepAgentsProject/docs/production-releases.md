# 生产发布与回滚

## 授权边界

- 角色权限和目标环境授权同时生效。非生产环境可在自己的环境内使用 `deployment.manage`；跨环境必须具有目标环境的显式授权。
- 生产发布始终要求已登记账号及显式 production `can_deploy` 授权，即使是平台/租户管理员，也不能直接绕过。
- 授权由当前项目的租户管理员或平台管理员维护；`owner`、`admin` 等项目角色不能自行授予生产权限。授权采用版本比较并记录变更前后值和原因。
- 发布授权不扩大运行数据的访问范围。开发环境的发布人可以申请生产发布，但不能因此读取生产会话、运行或产物。
- 审批需要 `release.approve` 角色权限及 production `can_approve` 授权；发起人与审批人的账号必须不同。不提供无审计的跳过审批开关。

## 对外接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/deployment-environment-grants` | 查看自己的授权；租户/平台管理员可查看当前项目全部授权 |
| `PUT /api/v1/deployment-environment-grants` | 更新某个项目账号在 development/staging/production 的发布及审批授权，须提交 version/reason |
| `GET /api/v1/agents/{agent_id}/release-channel` | 查看生产渠道版本及当前部署；读操作不创建记录 |
| `POST /api/v1/release-requests` | 创建生产发布/回滚申请，返回 202/PENDING，不部署 |
| `GET /api/v1/release-requests` | 权限过滤后的游标分页历史 |
| `GET /api/v1/release-requests/{id}` | 查看申请的冻结内容和状态 |
| `POST /api/v1/release-requests/{id}:decide` | 独立审批人 approve/reject，须提交 version/reason |
| `POST /api/v1/release-requests/{id}:cancel` | 发起人取消尚未处理的申请，须提交 version/reason |

`POST /agent-deployments` 仅创建非生产部署。旧客户端向此接口提交 production 将被拒绝，必须升级为申请/审批流程。

申请必须包含 `agent_revision_id`、`expected_channel_version`、`reason`。默认 `action=promote`，默认一小时过期，上限一天。回滚必须另指定 `action=rollback` 及 `rollback_deployment_id`，目标必须是该 Agent 以前经过审核的生产部署，且版本与申请一致。

支持 `Idempotency-Key`，限定在当前租户/项目/发起人。相同 key 和内容重试返回原申请；内容不同返回冲突。客户端网络错误不应盲目换 key 新建申请。

## 冻结、复核与原子应用

申请冻结发起人身份/角色、授权版本、Agent Revision、模型绑定的执行计划及哈希、评测证书及策略版本、生产渠道版本、相关意图路由配置摘要和被切换的路由名、变更原因与过期时间。

创建申请和批准时均要求可验证的模型 profile 绑定及当前有效、最新通过的评测。旧的仅有模型名称的计划在任何进程环境下都不能取得生产发布资格；开发模拟样本不构成生产验收证据。

批准时再次验证：

1. 两个账号仍有效；发起人保留所需角色及原授权代次，审批人当前仍有审批权。
2. 申请未过期、未取消、未被处理，版本和快照哈希正确。
3. 模型配置、价格绑定、执行计划、最新评测和评测策略未发生变化。
4. 生产渠道未被其他申请推进；意图路由配置未变化，新计划仍支持受影响路由的能力。

成功批准的数据库事务同时写入部署、生产渠道、申请决议、必要的新意图路由版本和审计记录。任何一步失败全部回滚。相同审批人重复提交完全相同的成功决议不会再次部署；竞争申请不能覆盖已经推进的渠道。

发布/回滚均创建新的部署记录，引用经审核的不可变 Agent 版本。旧 ACTIVE 部署转为 DRAINING：不接受新会话/新 Run，已有任务可继续执行及恢复。账号/模型撤销和执行隔离规则仍然生效。生产新任务准入与发布操作共享项目锁，避免检查旧部署后、切换完成才提交新任务的竞争。

现有意图路由中指向本 Agent 历史生产部署的目标会随批准一起更新，并创建不可变路由版本；不自动改写其他 Agent 的路由，也不修改已经冻结的历史路由决定。没有已有路由时不凭空创建新路由。

## 前端

控制中心的 **Production releases** 页面支持选择版本、申请发布或回滚、分页历史、查看计划/评测摘要、独立批准/拒绝、发起人取消，以及过期/冲突/无授权提示。Agent 发布弹窗选择 production 后进入该流程，不直接部署。

申请人看不到自己的批准按钮，服务端也独立拒绝自审批。批准前显示会影响的路由，并要求再次确认。授权管理目前通过 API 完成；完整组织成员/授权管理控制台及评测控制台仍是后续工作。

## Schema 15 与升级

迁移新增环境授权、申请、生产渠道及序列化锁表，在部署上增加 `release_request_id`。不会自动把已有角色转换为生产授权，也不会伪造旧部署的审批证书。

历史生产部署不再接受新会话/新任务，须用合规模型重新发布、完成评测并申请审核。已有运行按原有恢复和撤权规则继续执行。运维应先备份并清点生产任务、准备至少两个独立账号的授权，再安排受控升级；不要以直接修改数据库伪造批准。

本轮没有执行用户现有数据库迁移、重启服务、修改业务账号或自动授予生产权限。

## 验证边界

SQLite 与真实 PostgreSQL 测试覆盖授权、独立审批、账户/角色/授权撤销、版本及策略变化、过期、模型禁用、快照篡改、重复提交、并发审批、审计失败回滚、回滚和旧任务继续执行。UI 使用一次性本地账号、数据库与受控模型响应验证。

这些不是实际模型供应商、目标 Linux、Docker、mTLS 或对象存储生产验收。生产路由配置自身的独立变更审批已在 Schema 17 加入，见 [production-routing.md](production-routing.md)。多级审批链、定时发布、流量百分比灰度和外部审计防篡改存储仍未交付。
