# 生产意图路由变更与回滚

Schema 17 将生产路由配置变更纳入独立审批，不能再通过 `PUT /api/v1/intent-routing/profile` 直接修改。非生产环境保留原接口。生产发布已批准的部署不等于它自动取得某个意图的路由授权。

## 授权和用户界面

- 申请人须有 `routing.request`、`deployment.manage` 角色权限，以及当前项目 production `can_deploy` 显式授权。
- 审批人须有 `routing.approve`、`release.approve` 角色权限，以及 production `can_approve` 显式授权。
- `operator` / `release_manager` 新增申请和审批角色权限，但不自动获得任何环境授权，也不获得非生产路由直接管理权限。
- 发起人与审批人必须是不同账号；申请人可取消自己的待审申请，即使其生产授权已撤销。账号已禁用则不能继续操作。
- 授权继续通过现有环境授权接口管理。没有环境授权的项目 owner、admin 或平台管理员都不能直接生效生产配置。
- Settings 的 **Production routing reviews** 面板支持申请、原因、目标部署选择、阈值调整、前后配置对照、固定计划/评测证据、分页历史、独立确认批准、拒绝、取消和历史版本回滚。
- 发布控制面的跨环境授权不授予目标环境的会话、Run、产物访问权。

## API

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/production-routing/profile` | 已授权人员读取生产当前配置及候选部署，与当前登录环境无关 |
| `GET /api/v1/production-routing/revisions` | 权限过滤和游标分页的历史版本 |
| `POST /api/v1/routing-change-requests` | 创建不可变申请；202/PENDING，不立即生效 |
| `GET /api/v1/routing-change-requests` | 权限过滤和游标分页的申请历史 |
| `GET /api/v1/routing-change-requests/{id}` | 冻结的变更前后配置、证据和处理状态；不返回身份快照和原始内部记录 |
| `POST /api/v1/routing-change-requests/{id}:decide` | `version`、`decision: approve/reject`、`reason` |
| `POST /api/v1/routing-change-requests/{id}:cancel` | 发起人提交 `version`、`reason` 取消 |

更新申请必须包含 `expected_router_revision_id`、`reason` 和 `profile`。`profile` 包含 mode、两项置信阈值、决策有效期及四类目标部署；未指定的目标从已展示的基线补齐并冻结。未知字段/意图、非有限数值、无意义原因均被拒绝。申请默认一小时过期，上限一天。

回滚必须指定 `action: rollback` 和 `rollback_revision_id`，不能再同时提交 profile。只允许选择本项目曾经批准的生产路由版本，且以一个新的审批和新版本重新生效；不会覆写旧版本。若旧目标部署已经 DRAINING/停用，先按发布流程恢复合适的部署，再重新申请路由配置，不会自动复活旧部署或替换成未经本次审阅的新目标。

创建支持 `Idempotency-Key`，限定租户/项目/发起人并绑定内容。相同审批人以原版本、原动作和原原因重试已成功的决议，返回同一结果，不重复生效；改内容、改审批人或以最新版本重放旧决议不能冒充同一次操作。

## 执行和竞争边界

申请冻结：完整路由基线、拟生效配置、发起人角色和授权代次、目标生产部署和渠道代次、Plan Hash、当前通过的评测和策略版本、分类器身份、原因及过期时间。

批准在与生产发布/授权管理相同的项目锁下复核：两个账号、权限、授权代次、基线路由、目标部署是否仍是生产渠道当前部署、模型/评测证据和分类器身份。任何变化都要求新的审核。路由版本、申请状态和审计同一事务提交；审计失败也必须回滚路由。

生产发布/部署回滚会继续按已经审核的发布快照同步相关路由，并传递原路由是否已获批准的状态。不会把 LEGACY 路由洗成 APPROVED。待审批路由申请遇到已生效的发布会失效；反方向也一样。两类审批并发时只有匹配当前状态的一方能生效。

生产自动路由只使用批准配置中明确指定的目标，以及明确指定的 general 后备目标。没有配置某类目标时不会根据最新部署清单静默发现新的 Agent；没有 general 目标且无法匹配时返回冲突。`disabled` 是停止意图分类并使用指定 general，而不是禁止手动运行所有 Agent。要关闭自动入口，可以将所有目标显式设为 null 后审批。

路由决定提交为新 Run 时，再核对当前生产路由版本；旧决定必须重新分类。已经提交的决定幂等重试返回原 Run；已有 Thread 保留原部署，不重新分类。用户显式选定部署的运行仍服从原有生产部署、评测、资源权限和容量准入，不因路由审批获得额外权限。

## 升级与验收

Schema 17 为路由版本增加 `approval_state`，新增申请表和分页索引。旧配置/旧决策不删除、不重新写入为批准；旧和启动自动生成的生产配置标为 LEGACY，在独立审核前拒绝自动路由。读取初始配置仍可能生成候选配置记录，但此记录不是生产自动执行的授权。

正式升级必须先备份、准备至少两个独立授权账号，并安排独立迁移窗口。开发环境的自动迁移/热重载不是生产升级流程。本批未手动对用户现有业务数据库执行迁移或操作业务账号。

新增测试覆盖 SQLite/真实临时 PostgreSQL：直接修改阻断、历史配置不推定批准、权限与账号撤销、申请篡改、模型/评测变化、并发重复审批、跨项目隔离、过期、拒绝/取消、审计写入失败回滚、历史回滚、发布与路由竞争、旧决定失效及显式目标选择。浏览器使用一次性本地数据库与受控模型分别验证申请人和审批人，不使用真实业务身份。

此能力不代表已完成生产 Linux/Docker/mTLS/OSS 验收、分类器供应商行为验证、多级审批或外部审计防篡改；整体剩余工作见 [企业化实施状态](enterprise-hardening-status.md)。
