# 管理写入与撤权的一致性

## 修复的问题

请求进入时的登录和权限检查不能替代业务提交时的检查。原计费价格、配额、人工对账、模型注册/启停、评测集和策略写入存在“检查通过 → 账号撤权已提交 → 旧请求仍写入”的窗口。独立数据库上的定序回归已在旧代码上复现这七条路径。

本批增加 `packages/auth/transactions.py` 的 `authorized_write`，并接入以下控制面写入。不增加 Schema，不迁移业务数据库，不批量撤销现有会话。

| 写入 | 权限 | 事务内保护 |
| --- | --- | --- |
| 价格、配额、人工对账 | `billing.manage` | 操作者、用户配额目标、租户计费锁、账本和审计 |
| 模型注册、启用/停用 | `model.manage` | 操作者、模型变更、版本检查和审计 |
| 评测集、评测策略 | `evaluation.manage` | 操作者、用例/策略、版本检查和审计 |
| 评测结果发布 | `agent.publish` | 操作者、Revision/样本锁、结果、幂等记录和审计 |
| Agent 创建、草稿修改 | `agent.author` | 操作者、草稿版本及新增治理审计 |
| Agent Revision 发布 | `agent.publish` | 编译后的当前操作者、草稿版本、Revision/Plan 及审计 |
| ChangeSet 审核 | `coding.approve` | 操作者、Run/ChangeSet、版本和决策事件 |
| 非生产路由配置 | `routing.manage` | 项目协调锁、操作者、路由版本和新增治理审计 |

生产发布和生产路由仍使用已有独立审批、环境授权及项目协调流程；不会因本批新增普通路由保护而开放生产直改。

## 两种合法顺序

1. 撤权先提交：写入事务取得账号锁后重新读取账号、会话和范围，拒绝旧请求，不改变业务、幂等或成功审计记录。
2. 写入先取得账号锁：业务写入及审计作为同一事务完成；撤权等待后提交。撤权提交后，该旧身份不能再完成下一次受保护的写入。

PostgreSQL 使用与账号服务相同的用户行锁，多个账号按 ID 排序。用户配额同时锁定操作者与配额目标，避免目标转移项目期间使用过期的目标范围；互为目标的两次配额操作采用相同锁序。SQLite 使用写事务串行化。

锁定后再次读取有效身份；角色与传入快照取交集，超级管理员能力也不能从过期快照扩大。带本地会话的交互请求还检查强制改密和密码到期。事务收尾再次检查会话/密码时间条件，发现写入期间已到期则回滚业务和审计。后台执行不依赖浏览器会话，因此不能用这个入口替换 Run/摄取的租约和主体校验。

锁顺序不能随意嵌套：普通管理写入为账号 → 租户/资源；已有发布及路由协调操作为项目协调锁 → 有序账号 → 资源。拿到账号锁后不要再新增反向的项目协调锁。Agent 编译在写事务外进行，编译完成后重新授权并检查草稿版本，避免长期持有账号锁，也避免编译期间撤权后仍发布。

## 审计与返回

Agent 创建、草稿修改、Revision 发布新增 `agent.created`、`agent.draft.updated`、`agent.revision.published`；非生产路由新增 `routing.profile.updated`。记录操作者、资源、版本及计划/前版本标识，不复制 Prompt、模型密钥或完整草稿正文。已有账本、模型、评测及 ChangeSet 审计不重复伪造。

审计写入前后发生异常，业务状态均回滚。模型写入响应在同一事务内读取，避免把另一次并发更新后的状态误认成本次结果。原请求路径、参数、成功响应和乐观版本冲突语义保持不变；已撤销身份使用既有认证/授权错误处理。

这不是跨网络 exactly-once：提交成功但响应丢失仍需按具体接口的幂等/版本契约处理。也不证明已被供应商接受的调用能撤回，不改变人工对账的真实性边界。

## 验证与剩余范围

`tests/test_management_authority.py` 使用临时 SQLite 与独立 PostgreSQL Schema，覆盖角色/会话/账号/项目撤销的先后顺序、审计写入前后故障、写入期间会话到期、密码要求、配额目标转移及互为目标的竞争。`tests/test_control_plane_authority.py` 覆盖 Agent、评测结果、ChangeSet、路由以及编译期间撤权。使用合成账号和提供方，不操作业务账户，不把合成评测当作生产证据。

草稿并发测试改用两个独立数据库连接，先读同一版本再竞争提交；不在 SQLite 写锁内设置要求第二个写者进入的屏障。仍要求只有一个成功写者、版本只增加一次，缺少版本和过期版本依然拒绝。

该批不是“所有服务入口均完成撤权验收”的声明。仓库探测/快照等涉及外部 IO 的入口、后台在途外部副作用和资源策略变更仍需继续逐项审计与验证；不能仅在 HTTP 层检查一次，也不能把网络 IO 放入长事务来掩盖这些边界。SSO/MFA、组织成员关系、灾备审核接管、数据保留/回收和真实生产链路仍属于整体待完成工作。批次结果见 [实施状态](enterprise-hardening-status.md)。
