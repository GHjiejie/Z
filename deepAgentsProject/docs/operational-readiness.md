# 健康检查与任务容量

本页是已实现的代码契约，不是容量或生产基础设施验收报告。

## 存活与业务就绪

- `GET /livez` 只确认 API 事件循环能响应，不访问数据库或模型。用于存活探针，不能把 Worker 离线转化为所有 API 反复重启。
- `GET /readyz` 返回缓存的业务可用性；数据库异常、必需的 runtime/knowledge Worker 缺失、队列超阈值、等待过久或检测结果过期时返回 503。健康时返回 200。
- `GET /health` 使用相同就绪语义，旧的“数据库能查询就 healthy”已移除。非生产包含队列/Worker 数量及插件计数；生产仅返回状态、检查结果及时间，不公开模型地址、Worker ID 或内部错误。
- 两种就绪接口均禁用 HTTP 缓存。检测不调用付费模型，也不把“已配置”冒充“供应商服务可用”。当前直接检测范围为数据库、Worker 心跳/本地执行循环、任务积压；对象存储、扫描器和远程沙箱的端到端探测仍待补齐。
- 控制台 context/overview 的 Runtime 状态使用相同就绪结果；积压或检测失败不再仅因 Worker 心跳存在就显示健康，侧栏使用降级/异常状态颜色。

每个进程仅允许一个在途数据库检测。超时立即报告不可用，不因 HTTP 探针流量产生更多数据库线程；迟到结果被丢弃，完成后才能发起新检测。数据库连接池及 SQL 本身仍须配置有界超时。不要在连接串中取消生产超时设置。

Worker 心跳同时检查消费循环和恢复循环是否仍运行；循环已结束时登记 DEGRADED，而不是继续宣告 ONLINE。跨节点发现窗口受心跳（默认 15 秒）和过期时间（45 秒）影响；本地就绪检查可直接识别已结束的循环。

| 环境变量（统一前缀 `DEEPAGENT_HEALTH_`） | 默认值 | 含义 |
| --- | --- | --- |
| `INTERVAL` | 5 | 后台检测间隔秒数 |
| `TIMEOUT` | 2 | 检测响应超时秒数 |
| `STALE_AFTER` | 20 | 缓存最大年龄，必须大于间隔加超时 |
| `RUNTIME_QUEUE_LIMIT` | 1000 | 全平台等待任务数告警/就绪阈值 |
| `KNOWLEDGE_QUEUE_LIMIT` | 500 | 全平台等待摄取数阈值 |
| `RUNTIME_WAIT_SECONDS` | 300 | 当前待执行 Attempt 最长等待阈值 |
| `KNOWLEDGE_WAIT_SECONDS` | 900 | 最近进入 QUEUED 的摄取最长等待阈值 |

这些初始阈值用于可配置保护，不是经压测确认的服务能力。API 和 Worker 可独立启动，无 Worker 时仍可直接向 API 提交有界排队任务，但就绪状态不会报告业务正常。负载均衡应使用 `/readyz`，进程存活检查应使用 `/livez`，不要交叉使用。

## 任务准入

模型付费调用预算与任务容量是不同约束。创建 Run、人工重试、补充输入、审批后继续以及知识摄取/重试均检查任务容量；管理员无绕过开关。

容量检查与 Run/Attempt、审批决议、摄取状态和 PostgreSQL 队列写入位于同一事务。PostgreSQL 使用租户级事务锁，SQLite 使用本地事务锁，竞争请求不能一起占用最后一个名额。拒绝返回 `429 CAPACITY_EXCEEDED` 和 `Retry-After: 5`，不残留新 Attempt、幂等记录或已批准但未排队的状态。

Runtime active 指所有非终态任务，包含等待审批、等待输入和取消中的任务；queued 指 CREATED/QUEUED/ORPHANED/RESUMING。结束后自然释放名额。人工继续时排除当前 Run 后检查下一状态；重试的用户额度归属原任务发起人，不转移给操作人员。拒绝审批及取消仍可用于释放占用。已接受的任务自动故障恢复保留其 active 名额，不能为了排队限额而丢弃恢复工作；这种情况下队列可以暂时超过准入阈值并触发就绪降级。

所有配置统一使用 `DEEPAGENT_ADMISSION_` 前缀，各副本必须使用相同版本的配置；合法范围 0 到 1,000,000，0 表示关闭该范围的新准入。当前是运维配置上限，不是可按租户在线编辑的配额管理 API。

| 后缀 | 默认值 |
| --- | --- |
| `RUNTIME_TENANT_ACTIVE` / `RUNTIME_PROJECT_ACTIVE` / `RUNTIME_USER_ACTIVE` | 1000 / 200 / 100 |
| `RUNTIME_TENANT_QUEUED` / `RUNTIME_PROJECT_QUEUED` / `RUNTIME_USER_QUEUED` | 500 / 100 / 50 |
| `KNOWLEDGE_TENANT_ACTIVE` / `KNOWLEDGE_PROJECT_ACTIVE` / `KNOWLEDGE_USER_ACTIVE` | 200 / 100 / 20 |

Tenant 统计跨项目、环境；Project 统计项目内所有用户与环境；User 统计该租户内该用户。历史未知摄取发起人仍计入租户、项目容量，不伪造用户归属。Schema 16 为未完成任务建立部分索引，避免每次扫描全部历史数据；升级需要独立迁移任务，迁移只新增索引、不删除业务记录。

## 重试内容一致性

Run 创建和人工审批的幂等记录同时绑定规范化请求内容、用户、项目和环境；审批还绑定请求版本。相同 key、不同内容或主体返回 409。旧记录没有可信请求摘要时明确拒绝复用，不从后来已改变的任务元数据猜测原请求。客户端应先查询原操作状态，再决定是否发起新操作，不能遇到冲突就自动换 key 重做。

## 证据及后续范围

`tests/test_readiness.py` 覆盖 Worker 缺失、过期、消费循环退出、积压、等待超时、缓存、检测单次在途与迟到结果拒绝。`tests/test_admission.py` 覆盖 SQLite/PostgreSQL 并发最后名额、失败回滚、幂等重放、重试/继续/审批/摄取入口。

后续批次已加入 [解析进程隔离](document-parsing.md) 和 [日志、Trace、指标及告警规则](observability.md)，各自的目标 Linux/真实采集环境验收仍有待完成。租户公平调度、自动排队过期、上传与总存储配额、在线配额管理、完整依赖健康、实际告警通道和容量演练仍需继续补齐。不能把本页范围视为全部企业化目标完成。
