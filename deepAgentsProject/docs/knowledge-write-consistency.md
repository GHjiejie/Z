# 知识写入：事务一致性与请求重试

## 当前契约

知识库创建和上传准备在一个数据库事务内完成业务记录、事件与幂等记录。任意步骤（包括上传授权签发）失败则回滚本次新写入。支持 SQLite 和 PostgreSQL，不需要新增 Schema，也不会自动修补旧的半成品数据。

两个 HTTP 入口支持可选 `Idempotency-Key`：

```text
POST /api/v1/knowledge-bases
POST /api/v1/knowledge-bases/{id}/documents:prepare-upload
```

键长为 1–200，首字符为 ASCII 字母或数字，其余可包含字母、数字、`.`、`_`、`:`、`-`。无键调用仍可用于兼容客户端，但每次调用被视为新操作，无法防止响应丢失后的重复创建。正式客户端应在第一次发送前生成键，在结果不确定时保留原键，而不是每次重试生成新键。

- 作用域隔离租户、项目、环境及操作；上传操作还绑定知识库。
- 同键绑定当前发起人和完整的验证后请求内容。内容或发起人改变返回 409，不返回原请求的资源数据。
- 重试返回同一资源 ID 的当前可见状态，不能将它理解为原始 JSON 的逐字节重放。
- PostgreSQL 使用事务级键锁处理尚不存在的幂等记录；SQLite 使用写事务串行化。独立连接并发不会创建多份资源或事件。
- 写入和重试均在事务内重查权限。PostgreSQL 先锁定操作者用户，再锁定幂等键及资源，与账号/会话撤销的用户锁顺序一致。
- 幂等表只保存请求摘要、资源 ID 和契约版本，不保存请求正文、上传内容、签名 URL 或签名请求头。

## 上传授权生命周期

上传准备响应新增 `status`。首次创建的 `PENDING_UPLOAD` 返回 `upload`；同键重试在重新检查文档权限后，为同一对象按需签发新的短期上传地址。地址签发失败不会留下本次新建的文档、版本或事件。

一旦版本已进入 `UPLOADED`、`INGESTING`、`READY` 或 `FAILED`，重试返回 `upload: null`，客户端跳过上传，继续完成确认或使用已有任务的重试入口。PostgreSQL 对版本加锁，避免完成确认已经提交后，重试仍根据旧状态签发新上传权限。

这不会撤销之前已经签发、尚未到期的 OSS 地址。摄取仍须固定对象版本、校验内容摘要并执行文件安全检查。这里也没有宣称实现了累计存储配额或废弃上传回收；这两项仍属于后续数据生命周期工作。

Schema 20 的后续补强见 [上传容量治理](upload-governance.md)：已增加逻辑保留字节和待上传数量额度、固定意图期限及精确长度签名。过期返回 EXPIRED，控制台提示重新选择文件并结束旧重试键；已接受的校验任务不受意图过期影响。物理对象及全部历史版本的回收仍未完成，不能在未知对象是否删除时释放字节占用。

## 控制台

控制台在当前标签页的 sessionStorage 中保存请求指纹和随机操作键，不保存文件、标题、描述、认证令牌或上传地址。指纹包含用户/租户/项目/环境，上传还包含文件内容 SHA-256。

失败后重新提交相同内容，或刷新当前标签页后再次提交相同内容，会重用原键。只有收到创建成功或摄取确认成功后，才清除该操作键。成功后再次提交相同内容属于新操作。旧回调不会清除后续新操作的键。

清除浏览器会话存储或另开一个独立标签页不保证延续原操作；结果不确定时应先检查资源列表。存储读取/写入失败会阻止发送新请求，不能悄悄换键重试。文件内容不同即使名称和大小相同，也会得到不同操作键。页面另有同步提交锁，防止连续点击在状态刷新前重复发起流程。

## 验证

`tests/test_knowledge_atomicity.py` 覆盖业务表及事件写入前/后的故障、幂等记录故障、签发故障、请求内容与主体绑定、独立连接并发、权限撤销的两种提交顺序、文档权限变化、完成确认与重新签发的竞争，以及 HTTP 契约。

```sh
# PostgreSQL 用例只应连接专用测试数据库，各用例使用独立随机 Schema。
DEEPAGENT_TEST_POSTGRES_URL=<test-database-url> .venv/bin/python3.13 -m pytest -q tests/test_knowledge_atomicity.py
make test-web
make build
```

前端测试直接使用 Node 的测试运行器和 TypeScript 类型剥离，需要支持该能力的 Node（本次在 Node 25.6.0 验证）。`make verify` 已包含前端测试，但这不代表已补齐全部页面的组件/E2E 测试。

隔离浏览器夹具 `tests/browser_knowledge_fixture.py` 仅监听随机本地端口、使用一次性数据库与合成身份，故意丢弃首次成功创建响应，用于检查重试是否仍只有一份资源。该夹具不能部署为业务服务。

当前专项最终成绩和完整回归结果见 [企业化实施状态](enterprise-hardening-status.md)。本批修复的事务范围是知识库创建和上传准备，不应外推为所有控制面写入都已完成原子性审计。
